How a call flows

One turn, from the caller speaking to the agent speaking back. The green steps are the ones that run in Python — outside the model's control — which is where every compliance guarantee actually lives.

The compliance step is the point. A DNC check, calling-hours check and consent check all run in Python before the transport is attempted. The model is never asked whether it is allowed to make the call — so a prompt injection cannot talk the system into dialling someone who opted out. A test pins the ordering: a DNC number must be refused for being on the DNC list, not for a missing transport.

▭ End-of-turn is layered

Frame VAD, adaptive pause timing, a semantic/punctuation heuristic, and a contextual override. Trailing connectives — "und", "dhe", "and" — suppress end-of-utterance even after a pause, so a caller who pauses mid-sentence is not interrupted.

⚠ Untrusted data is wrapped

Retrieved knowledge is fenced in <<<UNTRUSTED_DATA>>> markers and labelled as data, not instructions. A document in the knowledge base cannot issue the agent orders.

☰ Simulated is labelled

When a real model is not available, the provider returns a simulated: true stamp rather than quietly producing plausible nonsense. Missing data is null, never 0.

The console

A Next.js 16 operations console — dark-first by design, with semantic colour tokens and WCAG AA contrast on every text/background pairing. Eleven routes, in English, German and Albanian.

These are real screenshots of a running system, not mockups. They were produced by scripts/capture_demo.py, which starts the API on a throwaway database, seeds realistic content through the public HTTP API, starts the console, and then signs in through the actual login form with a real browser before capturing. If any page failed to render — a redirect, an error screen, a missing marker — the harness would fail rather than ship the image.

Why voice does not run on the development machine

Measured, not assumed:

hardware probe
$ python scripts/dev.py hardware

CPU      Intel Core i3-1005G1 @ 1.20 GHz — 2 physical cores / 4 threads
RAM      7.7 GB total, ~1.6 GB free
GPU      Intel UHD Graphics — integrated, no CUDA
Profile  CPU_ONLY — below the spec's Profile A

LiveKit + Postgres + a local LLM + Whisper + TTS
simultaneously on 4 threads will not produce a conversational response.
This is a hardware limit, not a code-quality limit.

The most important caveat in this project. The voice pipeline is where nearly all the remaining risk lives — audio buffering, jitter, barge-in, codec negotiation, latency under load — and none of it has been tested. Treat every voice-adjacent claim in this repository as designed, not demonstrated.

✓ What is genuinely finished

  • The migration chain — proven by executing upgrade, check, downgrade and re-upgrade.
  • The worker — atomic claim, backoff and rescheduling all tested.
  • Multi-tenant isolation, on a real second organisation.
  • Compliance refusal ordering.
  • The licence gate, wired into CI.
  • The honest-degradation pattern itself.

⚠ What is left, by priority

  • The voice worker — the single largest gap. Not doable on this machine.
  • 176 tool implementations.
  • The pgvector retrieval path, unbenchmarked.
  • Cross-tenant tests for telephony resources.
  • Dashboard editing flows beyond create/publish/delete.
  • Email delivery for invites.

ℹ Known gaps we chose not to hide

  • Tool invocations are not persisted — an observability gap.
  • AI-disclosure text plays correctly, but the record that it played is not stored.
  • No browser-interaction testing; the sign-in form is rendered, never clicked.
  • Server Action dispatch is reviewed, not executed — Next's action wire protocol is internal and undocumented.
  • Docker images have never been built here.

Architecture

A monorepo. The provider abstraction is the load-bearing decision: swapping a simulated model for a real one is a provider registration, not a rewrite.

◉ Hardware-aware by design

The platform detects its own hardware profile and adapts. Three deployment shapes are supported: dev-lite on a laptop (SQLite, text-mode agent loop, simulation providers, full test suite, no containers), LOCAL on a 16 GB machine (Docker Compose core plus an optional LiveKit profile), and GPU (vLLM + faster-whisper + Chatterbox).

Nothing is faked to make a demo look better. Where a component cannot be exercised on the development hardware, the documentation says so and names the exact command a user with the right machine should run.

✓ What a reviewer should check first

  • docs/IMPLEMENTATION_STATUS.md — every number tied to how it was measured.
  • HANDOVER.md — what is done, what is not, and the traps.
  • docs/KNOWN_ISSUES.md — every limitation, named.
  • docs/TEST_REPORT.md — what the tests actually assert.
  • scripts/licence_gate.py — a gate that has failed before.

Run it locally

The backend and console run on an ordinary laptop with no GPU and no containers. Voice does not — that needs hardware this project was developed without.

bash
# 1. clone and set up the virtual environment + workspace packages
git clone <this-repo> && cd ai-call-agent
python scripts/dev.py setup

# 2. create the database and seed a first administrator
python scripts/dev.py migrate
python scripts/dev.py seed

# 3. start the API (uvicorn, reload)
python scripts/dev.py api

# 4. in a second terminal, start the console
cd apps/web && npm install && npm run dev
#    -> http://localhost:3000

Then verify that the state you cloned is the state that was claimed:

the gate
$ python scripts/dev.py verify

  -> licence gate: PASS
  -> lint:         PASS
  -> types:        PASS   (mypy, 95 source files, clean)
  -> tests:        PASS   (146 passed, 0 failed, 0 skipped)

VERIFY PASSED: licence gate, lint, types and tests are all green

Note on that output. On Windows the test step prints an override line, because the sandbox's bulk-delete guard intercepts pytest's teardown and pollutes its exit code. Rather than trust a lying exit code — or delete the step, which is how a never-run type checker once let four real bugs ship — the gate re-derives the verdict from pytest's own XML report. It was negative-tested: real failures, a corrupt report and an empty report all still produce FAIL.
